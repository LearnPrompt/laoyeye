# 逐字原则

## 为什么

把提示语改写成 Agent 风格的流程步骤，是 Skill 化最常见的做法，也是这个仓库明确不做的事。

这 12 条是成品。它们的效果来自三样东西，改写会同时毁掉三样：

1. **具体措辞。**「先不要给建议」和「请先分析再给建议」是两个不同的指令，模型的反应差别很大。
2. **追问节奏。**「每次只问一个问题，根据我的回答决定下一问，不要提前给我一整套问卷」这句话如果被压成一句「请逐步提问」，模型就会一次性倒出六个问题，整条提示语的价值当场归零。
3. **输出顺序。**「最后按以下顺序输出」后面那个列表就是产物的骨架。重排等于换了一个产物。

所以，仓库里的每一条原文都能追溯到作者发表的版本，两个 verify 就是那条追溯链的自动化。

## 收录来的 skill，同一条规矩

`vendor/` 下是上游的 pristine 副本，钉在具体 commit 上，配 `vendor.lock.json` 里每个文件的 sha256。`skills/` 下那五个目录整个是从 vendor 重放出来的，连 `references/` 和 `scripts/` 一起。

重放时只允许一类改动，全部声明在 `scripts/vendor.py` 的 `VENDORED` patches 里：**改名**。改名是为了避开跟上游仓库的重名，跟着改的还有正文里指向被改名 skill 的那一句（grill-me 里的 `Call the Skill tool with "grilling"`），不改它就指向一个不存在的 skill。

除此之外一个字符都不许动。上游改了就跑 `vendor.py pull` 同步，不是在这边手编。

## 边界

允许，因为都在代码块外面：

- 写「什么时候用它」，帮用户判断该不该拿这条。
- 写「用户要填的位置」，把 `【】` 占位符列出来。
- 写唤起触发词，那是 frontmatter 的 `description`，不是提示语。
- 写用法说明，比如提醒横纵分析法要配深度研究功能跑。

不允许：

- 改代码块里的任何一个字符。
- 把一条拆成多条，或者把多条合成一条。
- 翻译。原文是中文就保持中文。
- 加小标题、加编号、把段落改成列表、把列表改成段落。
- 在代码块里插入本仓库的说明、链接或出处。出处写在 README 致谢区。

## Agent 运行时也一样

`SKILL.md` 里的「怎么用」那段直接约束了执行行为：Agent 拿到这条提示语，是照原文做事，不是把原文当参考再编一套自己的流程。用户要原文时，整段原样输出。

这条如果守不住，仓库里的两道 verify 只是在校验一份没人真正执行的文本。
