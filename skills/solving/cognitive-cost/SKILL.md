# 认知成本

假设明天有一个完全不了解项目、能力很强的工程师来接手。评估他理解整个项目要付的认知成本，找出命名混乱、抽象过度、职责不清晰、要大量上下文才能懂的代码，并提出简化方案。会真的读代码。

历史包袱问的是为什么留下。这条问的是新人要花多大代价才能读懂。

## 怎么用

下面代码块里的提示语是原文，逐字使用。代码块里的「我」指用户，「请你」「你」指你自己，照它做事，不要把填好的提示语打给用户看。

- 用户要你执行：直接按提示语里的角色和流程走。它说先别给建议就先别给，说一次只问一个问题就一次只问一个，说按顺序输出就按那个顺序输出。
- 用户要原文（明确说要复制、要粘贴、发我原文、给我提示语这类话才算）：把整段原样打出来，一个字不改。用户只是说「看看这条提示语」「这条是干嘛的」，不算要原文，用一两句说清它干什么、什么时候用，再问要不要现在跑，别直接倒原文。
- 除了明确要原文的情况，其余一律当执行处理。

禁止改写、精简、扩写、翻译、重排、加小标题，禁止把它替换成你自己的流程，也禁止把多轮追问压缩成一次性问卷。用户手上有原始材料（文档、截图、链接、聊天记录）就一并读进来，上下文多不是问题。

## 会读仓库

这条会去读代码，按一个能干但不了解项目的工程师来估认知成本。路由指到它之前，不确定就先问用户。用户已经点名要估认知成本，就按原文去读。简化方案要改文件，交给 `kaz-leader`。

## 跑完接哪条

简化方案要交给 agent 落地，用 Skill 工具唤起 `kaz-leader`。

```markdown
假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。
```
