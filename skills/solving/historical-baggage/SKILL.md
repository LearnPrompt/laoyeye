# 历史包袱

要分清哪些设计是有意的，哪些是历史遗留，哪些是为了已经不存在的问题留下的，再识别可以安全移除的部分。会真的读代码库和 Git 历史。

洁癖对齐的是文档、规则和记忆。这条读的是代码为什么还在。

## 怎么用

下面代码块里的提示语是原文，逐字使用。代码块里的「我」指用户，「请你」「你」指你自己，照它做事，不要把填好的提示语打给用户看。

- 用户要你执行：直接按提示语里的角色和流程走。它说先别给建议就先别给，说一次只问一个问题就一次只问一个，说按顺序输出就按那个顺序输出。
- 用户要原文（明确说要复制、要粘贴、发我原文、给我提示语这类话才算）：把整段原样打出来，一个字不改。用户只是说「看看这条提示语」「这条是干嘛的」，不算要原文，用一两句说清它干什么、什么时候用，再问要不要现在跑，别直接倒原文。
- 除了明确要原文的情况，其余一律当执行处理。

禁止改写、精简、扩写、翻译、重排、加小标题，禁止把它替换成你自己的流程，也禁止把多轮追问压缩成一次性问卷。用户手上有原始材料（文档、截图、链接、聊天记录）就一并读进来，上下文多不是问题。

## 会读仓库

这条会去读代码库的 Git 历史和关键 PR。路由指到它之前，不确定就先问用户。用户已经点名要查历史包袱，就按原文去读。建议移除的部分要改文件，交给 `kaz-leader`，这条停在识别。

## 跑完接哪条

建议移除的部分要交给 agent 落地，用 Skill 工具唤起 `kaz-leader`。移除风险大，想先排雷，用 Skill 工具唤起 `inversion`。

```markdown
深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。
```
