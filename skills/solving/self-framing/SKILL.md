# 自建框架再自查

适合问题已经能说清，但直接要一个答案不放心，觉得套用现成框架会漏掉这件事特有的地方。

它先说清这是哪一类问题、好答案必须满足什么，再为这件事现写一套分析框架并亮出来，按框架跑完，检查自己漏掉的假设、视角、数据和失败方式，以及懂行的人会攻击哪里。最多改两轮就停。最后交最终答案、用过的框架、还剩下的已知未知。

专家会诊是几个角色互相质疑，这条只查自己刚才那份分析。事实核查去对说法的真假，这条把缺的证据记成已知未知。第一性原理把补丁拆回基本事实重推，这条不要求推倒重来。逆向法先列保证失败的做法，这条只在自查里点一条没想过的失败方式。苏格拉底式提问问的是用户，这条问的是自己的分析。

## 怎么用

下面代码块里的提示语是原文，逐字使用。代码块里的「我」指用户，「请你」「你」指你自己，照它做事，不要把填好的提示语打给用户看。

- 用户要你执行：先把本轮对话里用户已经说过的处境填进【】，只补真正缺的那一项，别让用户把说过的话再说一遍，然后严格照提示语里的规则做事。它说先别给建议就先别给，说一次只问一个问题就一次只问一个，说按顺序输出就按那个顺序输出。
- 用户要原文（明确说要复制、要粘贴、发我原文、给我提示语这类话才算）：打空白版，【】保持不填，一个字不改。用户只是说「看看这条提示语」「这条是干嘛的」，不算要原文，用一两句说清它干什么、什么时候用，再问要不要现在跑，别直接倒原文。
- 除了明确要原文的情况，其余一律当执行处理。

禁止改写、精简、扩写、翻译、重排、加小标题，禁止把它替换成你自己的流程，也禁止把多轮追问压缩成一次性问卷。用户手上有原始材料（文档、截图、链接、聊天记录）就一并读进来，上下文多不是问题。

## 跑完接哪条

已知未知里有一条会翻掉结论的说法要核实，用 Skill 工具唤起 `fact-check`。剩下的未知靠继续想补不上，用 Skill 工具唤起 `minimum-experiment`。自查说明整套做法是补丁摞补丁，用 Skill 工具唤起 `first-principles`。最终答案已经能派给 agent 干，用 Skill 工具唤起 `kaz-leader`。

```markdown
我要处理的问题是：【写清问题、背景、已知事实和约束】。

请不要直接给答案。先为这一件事现写一套分析框架，按它跑一遍，再检查自己漏了什么，改完就停。全程你自己做完。信息不够就记下来，不要改成反过来追问我。

按下面的顺序做。做完一节，写出来，再做下一节。

第一步，定性。
用几句话说明这是哪一类问题。然后列出一个好答案必须满足的几条。每条都要能拿来对照后面的答案，写得具体。空话比如「全面、深入、有洞察」不算数。

第二步，自建框架。
只针对这一个问题，把分析框架写成一段你接下来要严格执行的提示语，并完整展示出来。写清三样：
1. 要拆开看的几个维度，每个维度为什么非看不可；
2. 每个维度下要回答的问题；
3. 每个问题要什么证据。证据只从我已经给你的材料里取。材料里没有的，标成「还没有」。
SWOT、5W1H 这类现成格子，只有某一格确实咬住这件事才许留下，留下的要写明理由，咬不住的删掉。框架没亮出来之前，不要开始分析。

第三步，按框架跑。
严格照第二步写下的那段提示语，一个问题一个问题地答。有证据的，写下结论和依据。标了「还没有」的，不要用听起来像事实的话填上。

第四步，盲点自查。
对着第三步的结果，检查这份分析漏了什么。回答这四问：
1. 我默认了哪些前提。其中哪一条如果是错的，结论会翻掉。
2. 我没看的视角、没要的数据、没想过的失败方式，各写一条最要紧的。
3. 一个懂这行的人来挑这份分析，他最可能攻击哪一处，理由是什么。只借这一个眼光，不要派几个角色出来互相辩论。
4. 上面这些里，哪一条真会改变答案，哪一条改完答案还是原来那样。只处理会改变答案的。

第五步，修订。
只根据第四步里会改变答案的那几条，改一版答案。改的时候如果框架本身漏了维度，把框架一起改掉，并写明改了哪一处。改完再做一次第四步的自查。若还有会改变答案的漏洞，再改一次。最多改两轮。两轮用完，即使还有漏洞，也停。

停手后按这个顺序给出：
1. 最终答案。写明它满足第一步里的哪几条，哪几条仍没满足。
2. 你实际用过的框架。修订时改过的，给改过的那一版。
3. 还剩下的已知未知：你知道自己不知道、而且两轮里没补上的东西。
```

## 用户要填的位置

- `【写清问题、背景、已知事实和约束】`

用户没给全就先问缺的那一条，别自己替他编。
