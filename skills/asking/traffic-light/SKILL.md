# 红绿灯

卡尔的AI沃茨在 X 上发的「进度提示语」。核心思路：Agent 推荐下一步做什么，本身就是认知陷阱，它永远不会主动告诉你做完了。所以开工先钉住原始需求，每轮回复最后一行亮一盏灯。绿灯还差几项继续干，黄灯原始需求做完了、剩下的能串成一份下一轮计划，红灯做完了、剩下的零零碎碎存个档就结束。黄灯红灯都停手等你拍板。

跟乔哈里视窗、直给输出法一样是给整段协作定规矩，挂在会话或任务开头。乔哈里管先弄清楚要什么，直给管说话别绕，红绿灯管什么时候该停。

## 怎么用

下面代码块里的提示语是原文，逐字使用。代码块里的「我」指用户，「请你」「你」指你自己，照它做事，不要把填好的提示语打给用户看。

- 用户要你执行：直接按提示语里的角色和流程走。它说先别给建议就先别给，说一次只问一个问题就一次只问一个，说按顺序输出就按那个顺序输出。
- 用户要原文（明确说要复制、要粘贴、发我原文、给我提示语这类话才算）：把整段原样打出来，一个字不改。用户只是说「看看这条提示语」「这条是干嘛的」，不算要原文，用一两句说清它干什么、什么时候用，再问要不要现在跑，别直接倒原文。
- 除了明确要原文的情况，其余一律当执行处理。

禁止改写、精简、扩写、翻译、重排、加小标题，禁止把它替换成你自己的流程，也禁止把多轮追问压缩成一次性问卷。用户手上有原始材料（文档、截图、链接、聊天记录）就一并读进来，上下文多不是问题。

## 写代码的时候再加四条

原文管的是什么时候停。写代码时 Agent 还爱犯另外几种毛病，参考 multica-ai/andrej-karpathy-skills 里整理的 Karpathy 那几条观察，在代码块外补四条规矩，跟原文一起执行：

1. 先说假设。动手前把你对需求的理解和拿不准的地方列出来，有好几种理解就都摆出来，拿不准就问，别自己挑一个闷头写。
2. 能简就简。只写需求要的东西，不加没人要的功能、抽象和配置项。五十行能写完的别写成两百行。
3. 只动该动的。每一行改动都要能对上这次的需求，不顺手重构、不改格式、不删你没看懂的注释和代码。顺手看到的问题记进搁置，别直接改。
4. 先定验收标准。开工时把「目标」那一行写成能检查的标准，比如哪条测试要通过、哪个命令要跑出什么结果。标准全部满足就是做完，亮灯停手。

目标已经达成但还想再加点东西，按原文就是黄灯或红灯：停下来，把想加的写成计划或存档，等用户拍板，不要自己接着干。

这是写在代码块外的补充，原文未动。

## 跑完接哪条

这条是会话级设定，没有下游。可以跟 `johari-window`、`no-fluff-output` 一起挂在会话开头，互不冲突。亮了黄灯、那份后续计划要交给 agent 跑，用 Skill 工具唤起 `kaz-leader`。

```markdown
开工第一轮用一行钉住原始需求：
目标：A、B、C。
此后每轮只对照这份清单干活，清单只在我追加需求时才变。
每轮回复最后一行是进度条，三种状态：
🟢 还差：B、C｜ 搁置：X —— 原始需求有未达项，任务继续。顺手发现的改进只记进搁置，一行以内，先放着。
🟡 原始需求已全部达成。以下可做成下一轮 Plan —— 每项都附了证据。超出项能构成有明确目标和验收标准的后续计划，落盘成 plan/handoff 文件给路径，等我决定是否启动。
🔴 原始需求已全部达成，以下仅供存档 —— 每项都附了证据。超出项零散、不构成可执行计划，压成三行以内存档清单，结束。
黄灯与红灯的判定：超出项能否串成一个有清晰目标的 Plan？
能 → 🟡，
不能 → 🔴。
转黄/转红之后都停手，等我下指令。
我追加需求：更新目标清单，进度条回到 🟢。
```
